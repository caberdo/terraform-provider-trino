# trino_materialized_view Resource

Manages a materialized view. Trino only supports materialized views on connectors that implement them; the Iceberg connector needs a Hive metastore, because the REST catalog rejects CREATE MATERIALIZED VIEW. Read never refreshes the view.

## Example Usage

```terraform
resource "trino_materialized_view" "orders_by_region" {
  catalog = "iceberg"
  schema  = "sales"
  name    = "orders_by_region"

  # The query is resolved in the provider's session, so qualify table names.
  query = "SELECT region, count(*) AS orders FROM iceberg.sales.orders GROUP BY region"

  # Storage-table properties as raw SQL expressions; the provider quotes the
  # names and emits the values verbatim.
  properties = {
    format = "'ORC'"
  }

  grace_period = "1h"

  # Populate the view when it is created, and refresh explicitly by changing
  # refresh_token. Read never refreshes.
  refresh_on_create = true
  refresh_token     = "2026-10-26"
}
```

## Import

Import is supported using the following syntax:

```shell
terraform import trino_materialized_view.orders_by_region iceberg.sales.orders_by_region
```

## Schema

### Required

- `catalog` (String) Catalog that stores the materialized view.
- `name` (String) Materialized view name. The provider always quotes it, so the configured spelling is kept exactly.
- `query` (String) SQL query that defines the view, placed after AS. This is raw SQL, not a value: identifiers inside it are not escaped, and table references are resolved in the provider's session catalog and schema, so qualify them fully. Trino stores a normalised form of the query; the provider keeps the configured text in state instead of rewriting it from read-back, so a cosmetic normalisation never causes a diff. Changing the query replaces the view.
- `schema` (String) Schema that stores the materialized view.

### Optional

- `grace_period` (String) Grace period as a Go duration, for example 1h or 30m. Trino renders it as INTERVAL '<seconds>' SECOND. Write-only: Trino 476's SHOW CREATE MATERIALIZED VIEW does not return it, so the provider keeps the configured value and cannot detect an out-of-band change. Changing it replaces the view.
- `properties` (Map of String) Storage-table properties as raw SQL expressions, for example `{ format = "'ORC'", partitioning = "ARRAY['region']" }`. The provider quotes the property names and emits the values verbatim. Property names are matched case-insensitively. Read compares only the keys configured here against SHOW CREATE MATERIALIZED VIEW: Iceberg's derived values (location, format_version, storage_schema, ...) are ignored, and a configured property the server does not report is dropped from state so the difference surfaces as a plan. Changing the map replaces the view because Iceberg does not implement ALTER MATERIALIZED VIEW SET PROPERTIES.
- `refresh_on_create` (Boolean) Run REFRESH MATERIALIZED VIEW after CREATE so the view is populated. Defaults to true and is only used when the view is created.
- `refresh_token` (String) Change this value to run REFRESH MATERIALIZED VIEW on the next apply. Any string works, for example a timestamp. The provider never refreshes during a read, so a stale view is left stale until this changes, the view is replaced, or a scheduler refreshes it.

### Read-Only

- `id` (String) Identifier in the form catalog.schema.name.
